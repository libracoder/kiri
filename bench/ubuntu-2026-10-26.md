# Kiri vs the open-source engines on Ubuntu, 2026-10-26

One machine, one session, six engines measured minutes apart through the
same docker CLI (29.8.2; nerdctl through its own CLI), the same images,
warm. Every timing is a hyperfine median (30 runs for latencies, 5 for
transfers, 3 warm-ups); `bench/suite.sh` is the script, `bench/report.sh`
makes the table, raw hyperfine JSON is kept outside this repository.

Machine: a 16-core x86-64 PC, Ubuntu 24.04.4 as a WSL 2
distro (kernel 6.6.87, 32 GB), nothing else running. Not bare metal: the
scripts are plain bash and rerun unchanged on a native Ubuntu host.

| Engine | version | how it was reached |
|---|---|---|
| Kiri | main @ 181dde4, Linux-host engine | `kiri daemon`, its unix socket |
| Docker Engine | 29.9.2 static, containerd + runc | own `dockerd`, own socket, no service |
| Podman | 4.9.3, crun 1.14.1, rootful | `podman system service`, Docker API socket |
| nerdctl | 2.4.1 on containerd 2.4.1, runc, CNI | `nerdctl` CLI, buildkitd for build |
| Colima | 0.10.3, QEMU VM with 8 CPU / 8 GB, dockerd 29.5.2 inside | its docker socket |
| Docker Desktop | 29.8.2, WSL 2 backend | its WSL integration socket |

## What to say, and what not to

- Container start is 3.4× faster than Docker Engine, 5.9× faster than
  Podman, and the gap is stable across passes. On Windows (see
  `windows-2026-10-25.md`) the same engine starts a container in 78 ms.
- Container → host streaming is 3.7× Docker Engine; bind-mounted I/O is
  1.8× on writes and 2.9× on reads.
- `docker build` of a small Dockerfile is the fastest of the six.
- (1) Host → container stdin cannot be quoted: the agent caps pending input
  at 4 MiB and drops the rest (`crates/kiri-init/src/linux/agent.rs`,
  `MAX_PENDING_INPUT`); 200 MB piped in arrived as 1.2 MB. Fix with flow
  control, then re-measure.
- Published-port throughput is where Kiri loses: 10 Gbit/s against 100 for
  Docker Engine's iptables DNAT. Kiri relays published ports in user space.
  Fine for a web app, visible for bulk transfers over a published port.
- `exec` is only marginally faster than Docker and 3× slower than nerdctl,
  which talks to containerd directly.
- `pull` is Docker Hub network time; the spread is noise.
- Colima is a VM engine measured on Linux, where it has no reason to
  exist; it is here because it was asked for, not as a fair comparison.

## Reproduce

```sh
# tools: hyperfine, fio, iperf3, jq; engines on their own sockets, see install-ubuntu.sh
DOCKER_HOST=unix:///path/to/kiri/docker.sock   bench/suite.sh kiri
DOCKER_HOST=unix:///run/dockerd-bench.sock     bench/suite.sh docker-engine
DOCKER_HOST=unix:///run/podman-bench.sock      bench/suite.sh podman
CLI=nerdctl                                    bench/suite.sh nerdctl
bench/report.sh > table.md
```

## Engine-only latency (Docker API over curl, no docker CLI)

`bench/api.sh`: one lifecycle (create, start, wait, delete: four curl
calls, about 35 ms of curl+jq process cost included) and one exec (two
calls, about 19 ms included). hyperfine medians of 30.

| Engine | lifecycle | exec |
|---|---|---|
| **Kiri** | **33–47 ms** (engine ≈ 10 ms) | **17 ms** (engine ≈ 1 ms; curl returns at the 101 upgrade) |
| Docker Engine | 531 ms | 50 ms |
| Podman | 1010 ms | 120 ms |
| Docker Desktop | 579 ms | 70 ms |
| Colima | 523 ms | 67 ms |

Why this table exists: on this WSL distro the docker CLI binary alone takes
185–190 ms to start (`docker --version`, also the static 29.9.2 build on
local disk; `nerdctl --version` takes 16 ms). Every `docker …` figure above
includes that, so Kiri's CLI-side `run`/`exec` are 95% docker CLI. `kiri
exec` delegates to the docker CLI and costs the same.

## After the two fixes (same day, same machine)

Branch `stdin-flow-control`: stdin credit window (agent reports consumed
bytes, host blocks the client) and kernel-forwarded published ports on a
Linux host (nftables DNAT installed by the agent, user-space relay kept for
`--network host` targets and for the Mac VM). Two passes of `bench/suite.sh`:

| | before | after, pass 1 | after, pass 2 |
|---|---|---|---|
| 200 MB host → container | not valid, 1.2 MB arrived | **200 MB/s**, all bytes | **207 MB/s** |
| published port, iperf3 | 10.3 Gbit/s | **55.8 Gbit/s** | **58.0 Gbit/s** |
| `run --rm alpine true` | 188 ms | 214 ms | 230 ms |
| `exec … true` | 187 ms | 191 ms | 199 ms |
| 200 MB container → host | 209 MB/s | 144 MB/s | 197 MB/s |
| bind write / read | 1467 / 3851 MB/s | 970 / 3142 MB/s | 883 / 3075 MB/s |
| API lifecycle / exec | 33–47 / 17 ms | 36 / 18 ms | |

Stdin is now the fastest of the six engines (Docker Engine 129–163 MB/s).
Published ports match Podman and nerdctl, which use the same kernel path;
Docker Engine's 100 Gbit/s on a loopback binding comes from its proxy
sitting on `lo` with a 64 KiB MTU, not from DNAT. The other columns moved
within the day's noise (the docker CLI's own start varies 130–200 ms here);
the API-level numbers, which exclude it, did not move.

Verified live: loopback and all-interface bindings from 127.0.0.1 and the
LAN address (63.8 Gbit/s), UDP, HTTP, rules removed on `rm`, re-published
after a `--restart=always` restart, `--network host` still relayed.
